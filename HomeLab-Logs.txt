## 1. Infraestructura y Red (Networking)
Recuperamos un hardware antiguo y lo integramos a tu red actual.

* **Host (Gabinete):** Ubuntu Server 24.04 corriendo en un AMD Athlon II.
* **Conectividad:** Usamos un adaptador USB-a-Ethernet para darle red cableada.
* **Puente de Red (Bridge):** Configuramos Windows en tu PC nueva para que comparta internet con el gabinete. La IP quedó fijada (por ahora) en `192.168.0.10`.
* **Acceso Remoto:** Usamos el protocolo **SSH** (Secure Shell) para controlar todo desde PowerShell sin necesidad de periféricos físicos.

---

## 2. Portabilidad y Contenedores (Docker)
Este fue el salto de calidad. En lugar de instalar dependencias directamente en el sistema (que es sucio y difícil de replicar), usamos **Docker**.

### Conceptos Clave:
* **Dockerfile:** Es la "receta" de la imagen. Define que usamos Python 3.11, instala los `requirements.txt` y copia tu código.
* **Docker Compose:** Es el "orquestador". En un solo archivo YAML definimos que queremos dos servicios (Backend y Bot) corriendo sobre la misma red interna.



---

### 3. Variables de Entorno y Configuración "Pro"
Implementamos el estándar de la industria para que tu código sea **portátil**.

* **El problema:** En tu PC usabas `localhost`, pero en Docker el bot y el backend están en "cajas" distintas.
* **La solución:** Usamos `os.getenv()`.
    * En el **Bot**, el código busca la variable `API_BASE_URL`.
    * Si no la encuentra (en tu PC), usa `http://localhost:8000`.
    * Si la encuentra (en Docker), usa `http://backend:8000`.
* **Docker DNS:** Docker tiene un servidor DNS interno. Por eso, el bot puede llamar al backend simplemente por su nombre de servicio definido en el `docker-compose.yml`.

---

## 4. Persistencia de Datos (Volumes)
Como los contenedores son volátiles (si los borrás, perdés lo de adentro), usamos **Volumes**.
* Mapeamos `./database` del gabinete a `/app/database` dentro del contenedor.
* Esto asegura que tu base de datos SQLite `app.db` y tus archivos en `uploads/` sobrevivan a reinicios o actualizaciones del código.

---

## 5. Guía de Comandos para el Futuro

### Transferencia de archivos (Desde tu PC nueva):
Si modificás el código en VS Code, mandalo al gabinete con este comando:
```powershell
scp -r ./project mtopas@192.168.0.10:~/
```

### Gestión del Servidor (Vía SSH):
| Acción | Comando |
| :--- | :--- |
| **Actualizar y Reiniciar** | `sudo docker-compose up -d --build` |
| **Ver procesos vivos** | `sudo docker-compose ps` |
| **Ver logs en tiempo real** | `sudo docker-compose logs -f [nombre_servicio]` |
| **Apagar todo** | `sudo docker-compose down` |
| **Limpiar basura de Docker** | `sudo docker image prune -f` |
| **Apagar el gabinete** | `sudo shutdown now` |

---

## 6. Por qué esto es mejor que un `venv`
Aprendiste que pasar la carpeta `venv` es un error de novato porque contiene rutas absolutas de tu PC. Con Docker, el entorno se **construye nativamente** en el gabinete. No importa si tu PC es Windows y el servidor es Linux; la "receta" (Dockerfile) garantiza que el entorno sea idéntico.



---

## 7. Próximos pasos sugeridos
1.  **Frontend:** Ahora que el backend vive en la IP `.10`, tenés que configurar tu React/Vite para que apunte a `http://192.168.0.10:8000`.
2.  **IP Estática:** Si al reiniciar Windows la IP del gabinete cambia, el SSH se va a romper. Eventualmente, te convendría fijar la IP en la configuración de red de Ubuntu.
3.  **Seguridad:** Como es un Home Lab interno, estamos bien, pero si algún día abrís puertos en tu router, habrá que configurar un Firewall (`ufw`).
