## 1. Infraestructura y Red (Networking)

Recuperamos un hardware antiguo y lo integramos a tu red actual.

* **Host (Gabinete):** Ubuntu Server 24.04 corriendo en un AMD Athlon II.
* **Conectividad:** Adaptador USB-a-Ethernet (`enp0s7`) para red cableada hacia la PC Windows.
* **Acceso remoto:** **SSH** desde PowerShell sin periféricos en el gabinete.

### Arquitectura actual (post-recovery, mayo 2026)

Tras un corte de luz, un **Network Bridge** de Windows dejó el stack corrupto (Git, Cursor, APIs HTTPS y `ping github.com` fallaban; rutas a `169.254.x.x`). Se eliminó el bridge por completo, se reseteó la red de Windows y se migró a **Internet Connection Sharing (ICS)** — mucho más estable (NAT, sin bridging L2).

```text
Router
   ↓
PC Windows (NAT / gateway ICS)
   ↓ Ethernet 2
Ubuntu Server
```

| Rol | Adaptador / host | Detalle |
| :--- | :--- | :--- |
| Internet en Windows | `Ethernet` | Adaptador principal |
| Enlace al gabinete | `Ethernet 2` | ICS compartido desde Ethernet → Properties → Sharing |
| Gateway ICS (Windows) | `192.168.137.1` | Mini-router NAT |
| Ubuntu (DHCP ICS, transitorio) | `192.168.137.93` | IP que asignó ICS tras el recovery |
| Ubuntu (estática objetivo) | `192.168.137.10/24` | Ver netplan abajo |

**ICS en Windows:** en `Ethernet` → Properties → Sharing → activar *Allow other network users to connect through this computer's Internet connection* y elegir **Ethernet 2**.

### Recovery de red en Windows (si vuelve a romperse)

Ejecutar en CMD **como administrador**, luego reiniciar:

```cmd
netsh winsock reset
netsh int ip reset
netcfg -d
ipconfig /flushdns
shutdown /r /t 0
```

**No volver a usar Network Bridge** en este homelab — es frágil ante cortes de luz (duplicate IP, APIPA `169.254.x.x`, rutas zombie).

### IP estática en Ubuntu (netplan)

Archivo: `/etc/netplan/00-installer-config.yaml`

```yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    enp0s7:
      dhcp4: no
      addresses:
        - 192.168.137.10/24
      routes:
        - to: default
          via: 192.168.137.1
      nameservers:
        addresses:
          - 8.8.8.8
          - 1.1.1.1
```

Aplicar: `sudo netplan apply`

### SSH y SCP (usar IP estática cuando netplan esté aplicado)

```powershell
ssh mtopas@192.168.137.10
```

```powershell
scp -r ./project mtopas@192.168.137.10:~/
```

*(Antes del netplan estático la IP era `192.168.0.10` vía bridge; durante ICS transitorio: `192.168.137.93`.)*

## 2. Portabilidad y Contenedores (Docker)

En lugar de instalar dependencias directamente en el sistema, usamos **Docker**.

### Conceptos clave

* **Dockerfile:** Receta de la imagen (Python 3.11, `requirements.txt`, código).
* **Docker Compose:** Orquestador — backend y bot en la misma red interna vía un YAML.

---

## 3. Variables de Entorno y Configuración "Pro"

* **El problema:** En la PC usabas `localhost`; en Docker bot y backend están en contenedores distintos.
* **La solución:** `os.getenv()` — el bot busca `API_BASE_URL`; si no existe usa `http://localhost:8000`, si existe (Docker) usa `http://backend:8000`.
* **Docker DNS:** El bot llama al backend por el nombre de servicio del `docker-compose.yml`.

---

## 4. Persistencia de Datos (Volumes)

Los contenedores son volátiles; usamos **volumes**:

* `./database` del gabinete → `/app/database` en el contenedor.
* La SQLite `app.db` y `uploads/` sobreviven reinicios y redeploys.

## 5. Guía de Comandos para el Futuro

### Transferencia de archivos (desde la PC)

```powershell
scp -r ./project mtopas@192.168.137.10:~/
```

### Gestión del servidor (vía SSH)

| Acción | Comando |
| :--- | :--- |
| **Actualizar y reiniciar** | `sudo docker compose up -d --build` |
| **Ver procesos vivos** | `sudo docker compose ps` |
| **Ver logs en tiempo real** | `sudo docker compose logs -f [nombre_servicio]` |
| **Apagar todo** | `sudo docker compose down` |
| **Limpiar imágenes huérfanas** | `sudo docker image prune -f` |
| **Apagar el gabinete** | `sudo shutdown now` |

---

## 6. Por qué esto es mejor que un `venv`

Pasar la carpeta `venv` es un error: rutas absolutas de Windows. Con Docker el entorno se **construye en el gabinete**; el Dockerfile garantiza el mismo entorno aunque la PC sea Windows y el servidor Linux.

## Plan para subir de nivel (priorizado)

### Nivel 1 — Dejar de ser frágil (URGENTE)

* **Eliminar dependencia de Windows:** switch + cable directo al router (o IP fija en LAN del router).
* **IP fija:** netplan en Ubuntu (`192.168.137.10`) o reserva DHCP en router cuando haya switch.
* **Firewall básico (`ufw`):** permitir solo SSH; bloquear el resto.
* **SSH hardening:** deshabilitar password; solo claves.

### Nivel 2 — Convertirlo en sistema real

* Logs estructurados (no solo `docker logs`).
* Backups automáticos (`database/` + cron).
* Health checks — endpoint `/health`.

### Nivel 3 — Mentalidad pro

* Deploy automático (script o pipeline; menos `scp` manual).
* Separar dev / prod (aunque sea en el mismo server).
* Monitoreo básico (CPU/RAM, caídas de contenedor).
