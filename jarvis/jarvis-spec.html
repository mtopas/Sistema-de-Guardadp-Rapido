Especificación de proyecto

Jarvis 0.1 — Memory Core

Sistema operativo personal privado y agentivo. Esta versión establece la capa de memoria estructurada: captura, organización, persistencia y recuperación de conocimiento en lenguaje natural.

v0.1 En diseño Agosto 2026
01

Resumen del proyecto

Jarvis es un segundo cerebro personal construido alrededor de una memoria persistente bajo control propio. Ingiere información desde Telegram y una interfaz de escritorio, la organiza en tipos de memoria estructurada, y permite recuperarla mediante lenguaje natural.

Jarvis 0.1 es la primera versión funcional: implementa el Memory Core, la capa de memoria que distingue conocimiento en bruto, conocimiento consolidado, decisiones y contexto de proyecto. No es un chatbot, sino el comienzo de un sistema operativo personal.

El proyecto evoluciona desde SGR (Sistema de Guardado Rápido) mediante el patrón strangler: Jarvis nace dentro de SGR y va absorbiendo sus módulos de forma incremental, sin romper lo que ya funciona.

Principio fundacional

Jarvis no es una base de conocimiento que el usuario mantiene. Es un sistema que mantiene su propio cerebro. El usuario vive, trabaja y le manda cosas. Jarvis captura, entiende, organiza y recuerda.

02

Problema que resuelve

La Bóveda de SGR almacena y recupera notas, pero no construye memoria estructurada. Cuando el usuario pregunta "¿qué decidimos sobre RAFAM?", SGR devuelve fragmentos semánticamente similares — no una respuesta que priorice las decisiones tomadas, el contexto del proyecto o la evolución del conocimiento.

Las limitaciones concretas del sistema actual:

  • No distingue tipos de memoria: una decisión y una nota de lectura tienen el mismo peso en la recuperación.
  • No mantiene contexto conversacional persistente entre sesiones.
  • No organiza por proyecto de forma explícita — solo usa categorías planas.
  • No preserva la fuente original separada del conocimiento derivado.
  • No puede responder "¿por qué decidimos X?" porque no hay memoria de decisiones.

La diferencia que Jarvis 0.1 establece: transforma una captura en conocimiento organizado — identifica qué es, a qué proyectos pertenece, conserva la fuente original, y responde a "¿qué decidimos sobre X?" priorizando decisiones y contexto de proyecto sobre fragmentos genéricos.

03

Objetivos

Criterio de éxito de Jarvis 0.1

El usuario puede mandar información por texto o Telegram, cerrar todo y volver después, preguntar "¿qué decidimos sobre X?" o "¿qué sé de Y?" y obtener una respuesta que usa memoria persistente, útil y coherente.

Objetivos funcionales

  • Capturar información desde Telegram (mobile) y desde la interfaz /jarvis (desktop).
  • Guardar toda captura como RAW inmediatamente — nunca perder una entrada aunque falle el procesamiento posterior.
  • Clasificar automáticamente cada entrada: tipo de memoria, proyecto(s) relacionados, fuente.
  • Mantener un vault Markdown portable como fuente durable del conocimiento consolidado.
  • Recuperar memoria en lenguaje natural con ranking que prioriza decisiones y contexto de proyecto.
  • Mantener contexto conversacional persistente entre sesiones.
  • Controlar el presupuesto de tokens externos con límite diario configurable.
  • Migrar los datos de la Bóveda de SGR al Memory Core de forma controlada.

Objetivos arquitectónicos

  • Toda la configuración en variables de entorno — nunca hardcodeada.
  • Vault Markdown portable: si desaparece ChromaDB o Python, el conocimiento sigue existiendo.
  • Patrón strangler: la UI y API existentes de SGR siguen funcionando mientras el backend se reemplaza.
  • Arquitectura local-first que permita migrar a self-hosted (Docker Compose) en el futuro sin rediseño.
04

El usuario puede ver en /jarvis todas las entradas con su estado (PENDING / PROCESSING / DONE / ERROR), leer el error de las fallidas y reintentarlas manualmente.

CU-05 — Crear y explorar proyectos

El usuario puede crear un proyecto explícitamente o aceptar/rechazar uno propuesto por Jarvis. Puede listar proyectos, ver sus entradas asociadas y marcarlo como local_only.

09

Reglas de negocio

RN-01 — Captura indestructible

Una entrada RAW nunca se pierde aunque fallen Ollama, GPT o el procesamiento del vault. Si el guardado RAW falla, Jarvis notifica error. Si el procesamiento posterior falla, la entrada queda en estado ERROR y puede reintentarse.

RN-02 — Finanzas local-only por defecto

Toda información del módulo Finanzas de SGR es local_only = true por defecto. No se envía al modelo externo bajo ninguna circunstancia salvo que el usuario lo cambie explícitamente.

RN-03 — Privacy: bloquear ante la duda

Si el Privacy Gateway no puede determinar con certeza que un fragmento puede salir al modelo externo, lo bloquea. El sistema no asume permiso.

RN-04 — Proyectos: proponer, no crear silenciosamente

Jarvis puede proponer la creación de un proyecto cuando detecta suficiente información relacionada. No puede crear proyectos sin confirmación explícita del usuario. La declaración explícita del usuario siempre prevalece sobre la inferencia de Jarvis.

RN-05 — Presupuesto en USD, no en tokens

El límite diario es $1 USD. Jarvis calcula internamente cuántos tokens puede consumir según el modelo activo. Al agotarse, cae automáticamente a modo local y avisa al usuario. El usuario puede aprobar gasto adicional explícitamente; no se acola para el día siguiente.

RN-06 — Configuración en variables de entorno

Toda URL, puerto, API key, nombre de modelo y parámetro de infraestructura vive en variables de entorno. Nunca hardcodeado. El sistema debe funcionar sin cambios de código en homelab, VPS o cualquier entorno donde las variables estén correctamente configuradas.

RN-07 — Modelo configurable sin reiniciar

El modelo externo (JARVIS_EXTERNAL_MODEL) es configurable y no está atado a GPT-5.4 mini. Cambiar el modelo no requiere desplegar una nueva versión del código.

Estados del inbox (inbox_queue.status)

EstadoSignificadoTransiciones posibles
PENDINGGuardado, esperando ser procesado.→ PROCESSING
PROCESSINGEl worker está procesando activamente.→ DONE | → ERROR
DONEProcesado correctamente. Vault actualizado.Final (editable por usuario)

Al reiniciar el worker

Todo ítem en estado PROCESSING se resetea a PENDING. El worker nunca asume que un PROCESSING del pasado fue completado.

Casos borde

Ollama caído durante procesamiento

La entrada queda en ERROR. El worker reintenta con backoff exponencial (3 intentos). Si Ollama sigue caído, la entrada queda visible en ERROR en el inbox. El RAW nunca se pierde.

GPT call falla durante consulta

Jarvis cae automáticamente a Ollama para esa consulta y notifica al usuario. No se pierde la pregunta. Si Ollama también falla, Jarvis informa que no puede responder en este momento.

Vault no puede escribirse (disco lleno, permisos)

La entrada se queda en SQLite como DONE pero con vault_path = null. Se loguea el error. El conocimiento no se pierde (está en SQLite); solo falta el archivo Markdown. El worker puede reintentar la escritura al vault.

Mensaje ambiguo en Telegram

Jarvis responde con una sola pregunta: "¿Querés que guarde esto o que te responda?" El usuario responde; Jarvis procede según la respuesta. Si el usuario no responde en X minutos, Jarvis guarda como captura RAW (nunca pierde una captura potencial).

Regex detecta secreto en contexto a enviar

El Privacy Gateway bloquea el fragmento que contiene el patrón, no la consulta completa. Jarvis responde sin ese fragmento e informa que omitió un fragmento por razones de privacidad.

Captura menciona proyecto que no existe

Jarvis clasifica la entrada con el proyecto inferido como texto y propone crear el proyecto. Si el usuario lo rechaza, la entrada queda sin proyecto asignado hasta corrección manual.

Presupuesto agotado durante una consulta en curso

Si el presupuesto se agota mientras GPT está respondiendo, se completa la respuesta en curso. La próxima consulta ya usa modo local.

Duplicados

El worker detecta duplicados por hash del contenido durante el procesamiento. Si encuentra uno, lo marca como duplicado y no crea una entrada nueva en el vault. El RAW original se conserva.

Entrada pertenece a varios proyectos

Se permite. Una entrada puede tener múltiples proyectos en memory_entry_projects, con uno marcado como is_primary = true. El usuario puede cambiar esto desde el editor.

Manejo de errores

Principio

Nunca fallar silenciosamente. Todo error visible para el usuario a través de: estado en inbox, mensaje en Telegram, o indicador en la interfaz desktop.

Tipo de errorComportamientoVisibilidad
RAW no guardadoNotifica inmediatamente al usuario. No confirma recepción.Telegram / Desktop
Processing fallido (1-2 intentos)Reintenta con backoff. No notifica todavía.Solo logs internos
Processing fallido (3 intentos)Estado ERROR. Notifica al usuario que hay una entrada con error.Inbox view + notificación
GPT falla en consultaCae a Ollama. Responde con [modo degradado].Mensaje al usuario
Presupuesto agotadoModo local automático. Prefija respuestas.Mensaje de aviso
Secreto detectado por regexBloquea fragmento, no consulta. Responde sin él.Nota en respuesta
Ollama no disponibleInforma al usuario; no procesa inbox.Mensaje + estado sistema

Política de reintentos del worker

Backoff exponencial: 1 min → 5 min → 30 min. Después del tercer intento, estado = ERROR permanente hasta retry manual. El worker no bloquea otros ítems por un error individual.

Nueva ruta en SGR. Diseño futurista y tecnológico (especificación visual separada). Componentes:

  • Chat principal — conversación con historial visible, input de texto, citas de fuentes en las respuestas.

Patrón de transición SGR → Jarvis

La UI y API existentes de SGR (Bóveda, Finanzas, Agenda, Hábitos) siguen funcionando durante la transición. Los endpoints existentes funcionan a través de adaptadores de compatibilidad que internamente redirigen al Memory Core. Cuando el Memory Core madure, la Bóveda-UI pasa a ser simplemente una vista de la memoria de Jarvis.

Worker como proceso separado

El worker corre como un proceso Python independiente que hace polling de inbox_queue buscando entradas PENDING. Al arrancar, resetea cualquier entrada en PROCESSING a PENDING. Sobrevive a reinicios del servidor FastAPI y viceversa.

Seguridad y privacidad

Privacy Gateway (Jarvis 0.1)

Antes de enviar cualquier fragmento al modelo externo, el gateway aplica estas verificaciones en orden:

  1. Si memory_entry.local_only = true → bloquear.
  2. Si el proyecto asociado tiene local_only = true → bloquear.
  3. Si el fragmento coincide con regex de secretos evidentes → bloquear fragmento (no la consulta completa).
  4. Si pasa las tres verificaciones → puede salir como contexto RAG.

Regex de secretos (Jarvis 0.1)

Patrones mínimos para detectar secretos evidentes antes del envío:

# API keys y tokens comunes
sk-[A-Za-z0-9]{20,}           # OpenAI
ghp_[A-Za-z0-9]{36}            # GitHub PAT
xoxb-[0-9]+-[A-Za-z0-9-]+     # Slack Bot
Bearer [A-Za-z0-9._~+/-]+=*   # Bearer tokens
password\s*[:=]\s*\S+          # Contraseñas inline
api_?key\s*[:=]\s*\S+          # API keys inline

El detector completo de PII (DNI, CUIT, números de cuenta, teléfonos, etc.) se implementa en 0.2.

Categorías que nunca van al modelo externo

  • Entradas o proyectos marcados local_only = true.
  • Todo el módulo Finanzas (local_only por defecto).
  • Credenciales, tokens, contraseñas detectadas por regex.
  • Entradas marcadas confidential = true.
  • Datos de terceros sin autorización explícita.

Audit log mínimo (Jarvis 0.1)

Cada llamada al modelo externo registra: timestamp, modelo usado, cantidad de fragmentos RAG enviados, costo estimado. No registra el contenido enviado (es sensible), sino metadata de qué tipo de información salió. El audit log corre sobre OpenTelemetry — independiente del sistema LLM.

Principios de seguridad estructural (incorporados en 0.1)

Trust propagation sin degradación

El campo origin_trust de una fuente se propaga a todos sus derivados sin excepción. Resumir contenido web.untrusted diez veces no lo convierte en user.authenticated. Esta propagación es estructural: el campo viaja con cada claim y nunca puede incrementarse mediante consolidación.

Task Manifest

Antes de que el worker procese cualquier contenido externo, define un conjunto cerrado de capacidades permitidas. En 0.1 esto es un objeto Python que declara qué operaciones puede hacer el worker antes de empezar. Contenido encontrado durante la tarea no puede ampliar ese conjunto.

Memoria ≠ Permiso

Los permisos viven en un policy store separado que el LLM no puede escribir directamente. Un claim en el memory store que diga "el usuario autorizó X" no tiene poder de autorización. Esta separación es estructural desde 0.1, aunque el policy store de 0.1 sea mínimo.

Blast radius explícito para 0.1

El worker de background puede: leer conversaciones, escribir en el memory store. El worker de background no puede: hacer requests externos, leer credenciales, modificar el filesystem del host fuera del vault. Este blast radius es una restricción de diseño, no solo de configuración.

Provenance obligatorio

Todo evento escrito al memory store debe incluir source_id. No existe escritura válida sin provenance. Esto garantiza que cualquier claim puede responder "¿por qué Jarvis cree esto?" con una cadena trazar al mensaje o documento original.

Operación y mantenimiento

Quién administra el sistema

El único usuario es el único administrador. No hay soporte externo ni equipo de operaciones.

Procesos que deben correr continuamente

  • FastAPI (uvicorn) — servidor principal de la API.
  • Worker Python — procesamiento de inbox en background.
  • Telegram bot — proceso separado conectado a la misma API.
  • Ollama — servidor de modelos locales.

Se recomienda gestionar estos procesos con supervisord, systemd o el equivalente en el homelab. Los procesos deben reiniciarse automáticamente si fallan.

Tareas manuales esperadas

  • Corregir clasificaciones incorrectas del inbox (periódica, vía Telegram o desktop).
  • Crear proyectos que Jarvis no puede inferir solo.
  • Resolver entradas en estado ERROR en el inbox.
  • Backup manual de database/app.db y vault/ (hasta que haya backup automático).
  • Actualizar el modelo externo si cambia la oferta de OpenAI (solo variable de entorno).

Sin migración de esquema en caliente

Para Jarvis 0.1, los cambios de esquema en SQLite se aplican mediante init_db() al arrancar (mismo patrón que SGR). Las migraciones formales con Alembic se evalúan cuando el esquema esté más estabilizado.

Testing

Tests automáticos (unitarios)

  • Privacy Gateway: dado un fragmento con/sin flags, devuelve correctly bloqueado/permitido.
  • Regex de secretos: lista de patrones conocidos detectados correctamente; texto limpio no bloqueado.
  • Clasificación captura/consulta: casos representativos del árbol de decisión en Telegram.
  • Ranking de RAG: dado un conjunto de fragmentos, el ranker prioriza DECISION sobre RAW, proyecto explícito sobre general, reciente sobre antiguo.
  • Budget tracker: acumula correctamente, detecta EXHAUSTED, resetea al cambiar de día.

Tests de integración

  • Flujo completo de captura: mensaje entra → RAW guardado → worker procesa → vault escrito → estado DONE.
  • Flujo de consulta: pregunta → RAG → Privacy Gateway → respuesta con fuentes.
  • Resiliencia del worker: ítem PROCESSING al arrancar → resetea a PENDING.

Testing manual (calidad)

La calidad de las respuestas de Jarvis no puede verificarse automáticamente. El criterio de aceptación subjetivo es: dada una pregunta del tipo "¿qué decidimos sobre X?", la respuesta prioriza correctamente las decisiones del proyecto y no mezcla información no relacionada.

Riesgo de testing

El comportamiento del modelo externo puede variar entre versiones de GPT y no es determinista. No confiar en snapshots de respuestas como tests automáticos.

Riesgos

RIESGO 1 — Memory maintenance subestimado (Alta probabilidad, Alto impacto)

El roadmap pone Memory Maintenance en 0.2, pero detectar duplicados, contradicciones y conocimiento obsoleto de forma automática y confiable es uno de los problemas más difíciles de resolver incluso con modelos avanzados. Mitigación: el MVP solo requiere memoria que funcione bien — no perfecta. No comprometerse con mantenimiento automático antes de tener volumen real de datos.

RIESGO 2 — Migración de la Bóveda rompe datos (Media probabilidad, Alto impacto)

La migración de hojas/categorías al nuevo modelo de memoria puede perder información o romper las referencias existentes. Mitigación: backup completo antes del corte, preservar IDs originales, validar cantidades antes de confirmar que el Memory Core es fuente de verdad.

RIESGO 3 — Patrón strangler se prolonga indefinidamente (Media probabilidad, Media impacto)

Sin una fecha de corte para cada módulo, la coexistencia de SGR y Jarvis puede prolongarse hasta que ninguno esté completamente a cargo. Mitigación: definir explícitamente qué módulo se migra en cada versión y cuándo se eliminan los adaptadores.

RIESGO 4 — Calidad de clasificación con Ollama insuficiente (Media probabilidad, Media impacto)

llama3.2:3b puede no clasificar correctamente el tipo de memoria o el proyecto en casos complejos, requiriendo demasiadas correcciones manuales. Mitigación: evaluar GPT-5.4 nano ($0.20/M tokens) para clasificación como alternativa a llama3.2:3b — mejor calidad a costo muy bajo.

RIESGO 5 — Proyecto fracasa por falta de valor percibido (Media probabilidad, Alto impacto)

El usuario construye el Memory Core pero sigue encontrando más rápido buscar en la Bóveda existente porque Jarvis no responde mejor. Mitigación: definir el criterio de éxito subjetivo de 0.1 claramente (la pregunta de RAFAM) y no avanzar a 0.2 hasta que ese criterio esté genuinamente cumplido.

Restricciones

  • Stack: Python, FastAPI, SQLite, React 18, Vite, Zustand, Ollama, ChromaDB, Docker Compose, PyInstaller. No se introducen lenguajes nuevos en 0.1.
  • Infraestructura: solo homelab local en 0.1. No cloud, no multi-usuario.
  • Configuración: toda URL, puerto, API key y nombre de modelo en variables de entorno. Sin excepciones.
  • Portabilidad del vault: el vault Markdown debe ser legible y útil aunque no exista ChromaDB, Python ni Jarvis. Los embeddings son derivados reconstruibles, no la fuente.
  • Finanzas local-only: no negociable en 0.1. El módulo Finanzas nunca envía datos al modelo externo.
  • Sin agentes autónomos en 0.1: Jarvis no ejecuta acciones externas (mandar emails, modificar archivos fuera del vault, ejecutar código). Solo lee, organiza y responde.
  • Distribución: Opción 1 ahora (homelab). La arquitectura debe permitir Opción 3 (self-hosted Docker Compose) en el futuro sin rediseño.

Supuestos

  • El homelab está encendido 24/7 y accesible desde el teléfono vía Telegram.
  • Ollama está instalado con llama3.2:3b y nomic-embed-text disponibles.
  • El usuario tiene una cuenta de OpenAI con API key y acceso a GPT-5.4 mini.
  • El usuario usa Telegram activamente y no necesita una app nueva para captura móvil.
  • Los datos de SGR existentes son suficientemente valiosos para migrar al Memory Core.
  • La calidad de GPT-5.4 mini es suficiente para síntesis y razonamiento sobre memoria personal. Si no lo es, se puede cambiar el modelo sin cambiar el código.
  • El vault Markdown en disco es el mecanismo de backup implícito inicial; hasta que se implemente backup automático, el usuario es responsable de resguardar database/app.db y vault/.

Decisiones tomadas y su justificación

D-01
Modelo externo: GPT-5.4 mini, configurable
Mejor relación costo/calidad al momento de la decisión. El modelo no está hardcodeado — se configura con JARVIS_EXTERNAL_MODEL para cambiar sin tocar código.
Reversible
D-02
Presupuesto en USD, no en tokens
Los precios y modelos cambian. Un límite en USD es más estable y entendible que un límite en tokens que varía por modelo.
Reversible
D-03
Al agotar el presupuesto: modo local + aviso, sin cola
Acolar consultas para el día siguiente crea una experiencia confusa. El fallback local con aviso explícito es más predecible.
Reversible
D-04
Captura inbox-first: RAW inmediato, procesamiento en background
La captura nunca debe depender de que la IA termine correctamente. El usuario necesita certeza de que su información fue guardada.
Costosa
D-05
Worker como proceso Python separado con polling
Simple, sobrevive a reinicios del servidor FastAPI, sin dependencias adicionales (no Redis/Celery). Adecuado para volumen personal.
Costosa
D-06
Historial conversacional en SQLite; últimos 8-10 mensajes en cada consulta
La información estructurada (mensajes, timestamps, canal) encaja mejor en SQLite que en Markdown. El límite de 8-10 mensajes balancea contexto y costo de tokens.
Reversible
D-07
Contexto al modelo externo: solo fragmentos RAG, nunca el vault completo
Principio de mínimo contexto necesario. El vault completo nunca sale de la máquina.
Estructural
D-08
Patrón strangler para migración SGR → Jarvis
SGR sigue funcionando mientras el Memory Core crece. Reduce el riesgo de romper lo que ya funciona.
Estructural
D-09
Bóveda: refactorización progresiva en el lugar (Opción C)
Evita dos sistemas de memoria paralelos indefinidamente. La UI/API de Bóveda queda intacta; solo el backend de almacenamiento cambia.
Estructural
D-10
Migración de datos: Opción A (única, controlada)
Backup → script → validación → corte. Más trabajo por adelantado, pero deja el sistema limpio sin lectura dual ni estado inconsistente indefinido.
Estructural
D-11
4 tipos de memoria en 0.1: RAW, SEMANTIC, DECISION, PROJECT
Los 9 tipos del documento original son el objetivo final. En 0.1 estos 4 son suficientes para el criterio de éxito definido sin agregar complejidad innecesaria.
Costosa
D-12
Vault Markdown portable como fuente durable
Principio de portabilidad. Si desaparecen ChromaDB, Python o Jarvis, el conocimiento sigue existiendo en archivos legibles.
Estructural
D-13
Obsidian sync diferido a 0.2
Sincronización bidireccional confiable requiere watcher, resolución de conflictos y reindexado incremental. Para 0.1 alcanza con un vault Markdown interno legible.
Reversible
D-14
Proyectos: Jarvis propone, el usuario crea. Nunca silenciosamente.
Los proyectos son entidades con semántica propia. Crearlos silenciosamente generaría ruido y pérdida de confianza en el sistema.
Reversible
D-15
Finanzas: local_only por defecto, no negociable en 0.1
Información financiera es la categoría de más alta sensibilidad. La configuración por defecto segura es nunca enviarla externamente.
Estructural
D-16
PII detector completo diferido a 0.2; regex básicos en 0.1
Un detector completo de PII es complejo y tiene falsos positivos. Para 0.1, regex para secretos evidentes + flags manuales cubre los casos críticos sin agregar complejidad al flujo de captura.
Reversible
D-17
Interfaz desktop: ruta /jarvis en SGR, no app separada
Mantiene un solo frontend que el usuario ya conoce. Evita la complejidad de dos apps mientras Jarvis está en etapas tempranas.
Reversible
D-18
Distribución: homelab ahora, self-hosted Docker Compose después
Opción 1 para uso personal, Opción 3 si hay demanda de distribución. La arquitectura no debe cambiar entre las dos opciones — solo las variables de entorno.
Estructural
D-19
LiteLLM como gateway de modelos desde 0.1
El código de Jarvis nunca llama directamente a openai.ChatCompletion ni a ollama.chat. Todo llamado LLM pasa por LiteLLM. Cambiar modelo (precio, API, deprecación) pasa a ser una variable de entorno. El overhead es mínimo (wrapper HTTP) y la reversibilidad es alta.
Reversible
D-20
ChromaDB aceptable en 0.1; migración a pgvector en 0.2
ChromaDB es tolerable como índice auxiliar en 0.1 mientras el backend es SQLite. La migración a PostgreSQL + pgvector está planificada para 0.2. Esta decisión se documenta explícitamente para evitar que 0.1 crezca informalmente hasta donde la migración sea costosa. ChromaDB es un índice reconstruible, no la fuente de verdad.
Costosa
D-21
Langfuse y OpenTelemetry como observabilidad desde 0.1
Langfuse (self-hosted) provee trazas LLM necesarias para depurar el Memory Core desde el primer día. OpenTelemetry provee trazas de infraestructura y el security audit log, independiente del sistema LLM. El costo operacional en homelab es mínimo. Agregarlos después implica instrumentar código ya escrito.
Reversible

Preguntas que permanecen abiertas

  1. ¿GPT-5.4 nano para clasificación? La clasificación de intención y extracción de entidades está diseñada para Ollama, pero GPT-5.4 nano ($0.20/M tokens) podría ser significativamente mejor. Evaluar en la primera implementación del worker.
  2. ¿Cómo de tolerante es el límite de 8-10 mensajes? ¿Es el contexto conversacional correcto para el tipo de conversaciones que el usuario tiene con Jarvis, o se necesita más (o menos)?
